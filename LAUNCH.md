# Launch and side-income plan

All dates below are relative to starting the work. Prices, targets and revenue scenarios are hypotheses. No customer acquisition, sponsorship, payment or release has happened.

## First 12 weeks

| Period | Work | Evidence to save |
|---|---|---|
| Weeks 1-2 | Interviews, three manual reports, a fixed-scope paid offer; F1 if engineering is requested. | Dated feedback, real issue examples, report reviews, offer response. |
| Weeks 3-6 | Implement F1-F5 around demonstrated useful findings. | Acceptance records, independent calculations, permissioned/live smoke results. |
| Weeks 7-8 | Complete F6; prepare alpha, demo, README, sample report and contributor guide. | Packed-install rehearsal, platform results, actual publication links if released. |
| Weeks 9-12 | Publish permissioned case studies; offer audits and implementation; measure repeat use. | Outcomes with limitations, active repos, repeat runs, paid work. |

Preparing artifacts is reversible local work. Publishing a package/site, posting promotions, contacting people, or deploying requires the relevant user authorization. Do not ask for approval of a vague plan when a concrete artifact can be prepared first.

## First commercial offers

| Offer | Price to test (USD) | Scope and limits |
|---|---:|---|
| OSS CLI | Free | Local collection, analysis, reports and comparison. |
| CI audit | $300-750 | One repository, bounded history, up to three evidence-backed findings, one review session. No savings guarantee. |
| Implementation | $500-2,000 | Separately scoped changes and verification in the customer's repository; permissions and change review agreed first. |
| Hosted reports, later | $29-79/org/month | Only after repeat demand: scheduled reporting, history and shared access. |
| Sponsors/donations | Optional | Support maintenance; not the initial revenue forecast. |

Keep free core features useful. Sell saved setup/interpretation work, service, or ongoing convenience. Publish support boundaries to protect side-project time; avoid an early uptime commitment.

Illustration only: 20 customers at $49/month equals $980 gross MRR before costs/taxes/churn. Two $500 audits produce $1,000 in one-time gross service revenue, not recurring revenue. Track delivery hours and support time alongside income.

## Community launch materials

- README: sample report, installation, permissions, data handling, limitations, quick start and uninstall.
- Small synthetic demo repository/fixture showing a useful investigation, clearly labeled synthetic.
- Short recording using implemented commands; no staged claims of customer impact.
- One technical article explaining a measured intervention, with permission if real customer data is involved.
- CONTRIBUTING, CODE_OF_CONDUCT, SECURITY reporting instructions, actual LICENSE, issue/PR templates, and documented supported runtimes.
- Starter issues for documentation, fixtures and well-specified analysis rules; keep the core data contract stable.

Relevant channels include CI communities, GitHub Discussions, technical blogs and existing professional contacts. Prepare posts before seeking any required publication authorization; respect community rules and do not send unsolicited tool-driven messages.

## Growth and stop/adjust rules

Measure repositories completing the full flow, repeat runs, useful findings acted on, retained paying organizations, revenue by type, and time per customer. Local users need not accept telemetry: use opt-in feedback and aggregate hosted data only if a hosted product exists and its privacy terms support it.

After the first pilot cycle, investigate why users did not return. Occasional audits can support a service business. Persistent recurring use can justify scheduled reports. If native tools already satisfy the need, change the report/audience before expanding infrastructure. Do not interpret GitHub stars or downloads as paid retention.
